## 2026-06-15

### Did

- Deep-dived the cross-sectional interface options across established engines:
  - **backtrader:** universal `next()` via `self.datas`; single-asset is the
    degenerate one-feed case; stateful callback model
  - **zipline:** Pipeline (cross-sectional factor computation) separated from
    `handle_data` (order placement); docs are explicit that this separates
    alpha-factor computation from order logic
  - **Lean:** Portfolio Construction Model (Insights → PortfolioTargets)
    separate from Execution Model; holdings-agnostic allocation is the
    explicit design goal
  - **bt:** pipeline of algos (Select → Weigh → Rebalance) gated by a Run
    algo; the gate model cleanest for a daily-bar engine
- Resolved the sibling-vs-unified-method question: **the stateless purity
  contract (`ADR 0004` decision 3) is what forces the sibling shape**, not
  the ABC lock. backtrader's universal `next()` is ergonomic because its
  strategy is a stateful callback; copying that shape while having rejected
  its mechanism is not available to this engine.
- Confirmed the score-grade taxonomy: cardinal (real magnitude) / ordinal
  (rank only) / binary (eligible / not); the adapter can only express binary;
  momentum is native because the trailing return *is* the signal

### Learned

- **backtrader's universal `next()` is a genuinely clean design that is
  deliberately given up.** This is not a workaround — it is a conscious
  trade: a provably testable no-lookahead guarantee over a cleaner universal
  method. Worth stating explicitly in the ADR so future readers understand
  the engine's design character.

- **`CrossSectionalAdapter` value is concentrated in Phase 4 and expected to
  fade.** Its purpose is to let classical binary single-asset strategies
  appear in portfolio results without re-deriving the lookahead argument;
  Phase 6 ML strategies are inherently cardinal and will all be native
  `CrossSectionalStrategy`. Build it deliberately thin.

- **The allocation boundary must be holdings-agnostic.** An allocator that
  peeks at current positions cannot be swapped without re-reasoning execution.
  The clean invariant: scores → target weights; the reconciler owns the diff.

## 2026-06-16

### Did

- Researched TWSE settlement mechanics: T+2 Delivery-versus-Payment with
  daily multilateral net settlement; no general prefunding requirement; a
  same-day sell and buy produce a single net cash obligation on T+2
- Drafted and finalized **ADR 0005** (instant-settling cash pool,
  sell-before-buy ordering):
  - Instant model is *justified by*, not *modelled on*, T+2 net settlement
  - Sell-before-buy dominance proof: sells first maximises available cash for
    the buy phase; when cash is not binding, ordering is irrelevant; so
    "always" and "only-when-tight" are outcome-equivalent, and "always" is
    simpler and more testable
  - Named the five assumptions (immediate proceeds, no prefunding, every trade
    settles, free T+2 float, single fill point) and the phase that breaks each
  - The concrete current failure mode: `min(target, cash)` buy sizing on a
    rotation silently under-invests if sells don't run first

### Learned

- **"Sell before buy is weakly dominant" has a clean proof.** Available cash
  is maximised by running sells first; buy size is monotonic in available
  cash; therefore every buy is at least as large as under any other
  interleaving. The proof removes the need for a conditional "only when tight"
  branch — two equivalent rules, always prefer the simpler one.

- **The instant model and the T+2 model produce identical realised books for
  a long-only strategy spending within netted means.** The settlement lag is
  invisible to P&L precisely because the strategy never depends on the gap
  between "cash I hold" and "cash I am owed." Modelling the lag adds
  machinery for zero P&L difference at this phase — defer it.

  - Configurability tier hierarchy: pure-reporting knobs vs return-changing
    policy vs structural invariants

  decisions, 14-step build sequence, test strategy, rebalance loop mechanics,
  turnover economics, exit criteria, pitfalls
- Updated **CLAUDE.md**: D5–D11, Phase 4 module layout, strategies/ import
  boundary, new guardrails, Phase 4 public API surface

### Learned

- **Trade accounting has two distinct questions that need two distinct
  mechanisms.** "What is the book worth each day?" → mark-to-market with
  `Position.avg_cost` (already implemented). "When a trade closed, did it
  win?" → lot ledger pairing closed exits against entries. They are not
  alternatives; they answer different questions. `avg_cost` and the lot ledger
  are both kept.

- **The `RebalanceContext` object is the right abstraction even for Phase 4's
  calendar-only case.** Calendar rules only read `ctx.date`; the richer fields
  exist so threshold rules (read drift) and event rules (read signal_changed)
  drop in later without reshaping the calendar implementations. This is the
  same pattern as `ADR 0004`'s `Literal["next_open"]` — build the seam right
  the first time.

- **Cadence, not the signal, often decides portfolio viability.** Monthly
  rebalancing on a top-10 portfolio can bleed ~7% per year to the 0.3% sell
  tax alone before any alpha. That is itself a finding worth reporting, not
  hiding. The tear sheet must surface turnover and total fees.

### Learned

- **The build-sequence dependency is explicit when one module imports another.**
  The wrong order (allocator before tiebreak) would have caused an import error
  as soon as `EqualWeightTopN(tiebreak=...)` was wired up. Catching it at the
  spec level is better than at the import level — fix the spec before the code
  diverges from it.

- **`CrossSectionalAdapter` value is intentionally limited.** It produces binary
  scores (0 or 1), not cardinal magnitudes. Two tickers with `score=1.0` are
  treated identically by any downstream allocator; the adapter cannot express
  "this ticker has a stronger signal." This is not a bug — it is the correct
  boundary between the binary `Strategy` interface and the cardinal
  `CrossSectionalStrategy` interface. Document it clearly so future readers do
  not try to extend the adapter to carry magnitude.

- **`RebalanceContext` is the right abstraction even when only `ctx.date` is
  used.** Calendar rules remain stable as threshold and event rules are added
  later — same pattern as ADR 0004's `Literal["next_open"]` seam.

## Retrospective

### What went well

- **4a strategies (Steps 1–6) were fast.** Five strategies in one session because
  they share the same three-part shape: copy bars, compute indicator, return
  signal series. Once the first two were right, the rest were substitutions.
- **ADR 0007 surfaced a real data gap before it could corrupt results.** The
  0050 stock split on 2025-06-18 would have silently produced a −99% CAGR for
  the benchmark. Discovering it during Step 8's first real-data run and
  immediately writing a design document was the right response.
- **The workaround (`end=2025-06-17`) is minimal and well-bounded.** All three
  known splits fall after that date; the evaluation window is clean and the fix
  is a pre-Phase-5 ticket, not an emergency patch.
- **Steps 9–12 landed in one session.** The ADR 0006 design work from the
  planning session paid off — each module had a clear spec, so implementation
  was mostly transcription with a few small discoveries.
- **The build-sequence swap was caught before any code depended on the wrong
  order.** Fixing the spec first, then the code, kept the commit history clean.

### What was harder than expected

- **The stock split investigation was a significant detour.** Discovering the
  data gap mid-session and fully investigating it (FinMind endpoint, universe
  probe, ADR write-up) consumed most of a day. Worth it for correctness, but
  the scope was larger than anticipated.
- **The `CrossSectionalAdapter` naming and boundary needed extended discussion.**
  The distinction between `SmaCrossover` and `CrossSectionalAdapter(SmaCrossover())`
  is semantically significant — they answer different questions and must never be
  conflated — but that distinction is not obvious from the code alone. Time spent
  on docstrings and discussion was necessary to keep the codebase interpretable.

### What to carry forward

- The `InsufficientCashError` handling gap in the cross-sectional engine is a
  known limitation: the reconciler sizes buys on equity without accounting for
  transaction costs, so sequential buys from a fully-invested portfolio can
  overshoot available cash. Document in the Phase 4 retro; implement in Phase 5
  where partial-fill and order-rejection semantics are already in scope.
- ADR 0007 (stock split fix) is a pre-Phase-5 prerequisite — implement before
  the evaluation window is extended past 2025-06-17.
