## 2026-07-21 (Tuesday)

### Did

- Fixed a real cross-account bug: `NettingSettlement`'s `bar_net`/`bar_date`
  accumulator lived on the `SettlementModel` instance itself, but
  `BrokerSimulator`'s internal account and `PaperSession`'s own account are
  constructed with the *same* `SettlementModel` instance — so every trade
  was being netted twice. Moved the accumulator onto each account's own
  `DatedLedger`, making `NettingSettlement` fully stateless and the two
  accounts independent again. Also added `SettlementModel.on_bar_start`/
  `close` (default no-op) so a settled day's net flushes as soon as the
  next trading day rolls in, rather than waiting on a later trade to
  trigger it — the prior design left a run's final trade (always the
  forced-liquidation sell) permanently unflushed, understating
  `total_value`
- **Step 11** — `tests/broker/test_oracles.py`, the Phase 5 correctness
  gate: O3 (order-quantity conservation), O5 (cash), O6 (share), and O7
  (cost) built net new, each recomputing its expected answer from a flat
  tally over the recorded event log rather than trusting
  `BrokerSimulator`'s own incrementally-maintained totals; O1, O2, O4, O8,
  O9, O10 re-verified end-to-end through the full simulator, alongside
  their existing fold-level unit coverage
- Fixed `SettledCashOnly` debiting both buy and sell cash deltas at T+2
  when only sell proceeds should be deferred — a buy spends cash already
  on hand and has nothing to wait on. The bug made `SettledCashOnly` less
  conservative than `NettingSettlement` on the buy side immediately after
  a purchase, the opposite of its intended pessimism. Fixed by branching
  on `cash_delta`'s sign in `on_trade`

### Learned

- **Sharing one `SettlementModel` instance between two accounts is a
  trap for any settlement model that carries its own per-bar state.**
  `NettingSettlement`'s accumulator needing to move onto `DatedLedger`
  (each account's own state) rather than staying on the shared model
  instance is the general lesson: a `SettlementModel` must stay stateless
  itself, with all state living on the ledger it's handed, precisely
  because the same instance is legitimately shared.
- **Building the independent-oracle suite immediately surfaced two real
  bugs** (the netting double-count, the `SettledCashOnly` debit timing) —
  concrete evidence for ADR 0008's own justification for the oracle
  design: correctness checks that recompute independently *can* fail,
  unlike zero-pessimism reproduction against the same shared core.

### Learned

- **`total_value()` missing `bar_net` is exactly the same class of bug as
  the `NettingSettlement` accumulator issue from Tuesday** — anywhere
  `NettingSettlement`'s same-day-net state exists, every equity/value
  computation has to know to include it, or `InstantSettlement`-only test
  coverage will never catch the gap.
- **Storage design for a small, externally-growing reference table should
  match the codebase's existing pattern for structurally identical data,
  not invent a new one.** Suspension halts are shaped exactly like
  corporate actions (sparse, per-ticker, dated events from TWSE) — the
  right storage design was "do what `write_corporate_actions` already
  does," discovered only after first proposing a JSONL-in-`src/` design
  that didn't fit the project's data/code separation.
- **`LiveFeed` and a future `LiveSession` are easy to conflate but solve
  different problems** — `LiveFeed` is still a full simulation (current
  market data, no real trades); `LiveSession` is real broker, real money.
  Getting this distinction precise mattered because it changes which
  state-recovery mechanism is even valid: replay works for a simulator
  where everything is a deterministic function of stored bars; it cannot
  work once real fills carry information bars can't reconstruct.
- **A schema migration doesn't retroactively fix already-stored files.**
  `write_*` validates against the current schema; `read_*` does not — so
  old Parquet files written before a column was added just silently lack
  it until deliberately re-backfilled. The `pay_date` gap sat unnoticed
  since W27 until step 13 actually exercised `ReplayFeed` against the real
  local store for the first time.
- **`backfill.py`'s default ticker list and the anchor-fixture ticker list
  are not the same set.** Ticker `1101` exists only to support the
  adjustment-anchor regression test and is invisible to any operation
  scoped to "the Top 50" — a wipe-and-rebuild of shared local storage can
  silently orphan it unless that's specifically remembered.

### Learned

- **A stub return value (`Decimal(0)`, `pd.DataFrame()`) left over from an

  not correctness.

### Did

  replay data surfaced two corporate-action crashes the hand-built fixtures
  never exercised: `RIGHTS_ISSUE` and `CAPITAL_REDUCTION` both raised

  `rejection.py::_ex_day_reference`. Both are common enough in the Top 50

- **ADR 0012** — resolved the two action types with genuinely different
  treatments after tracing the actual economics: `RIGHTS_ISSUE` is a real
  shareholder *choice* (subscribe, sell the rights, or lapse), modeled as an
  always-no-op lapse in `decompose` plus a TERP-formula reference price in
  `_ex_day_reference`; `CAPITAL_REDUCTION` turned out to be unambiguous in
  this dataset — FinMind's rows are always the share-cancelling kind
  (`cash_amount` always `NaN`), structurally identical to `STOCK_SPLIT`
  (`ADR 0007` already established the same ratio convention) — so it got a
  real `ShareMutation`, not a lapse, folded into `STOCK_SPLIT`'s existing
  branches
- Fixed a `Decimal ** float` `TypeError` in `reconcile.py::_as_backtest_result`
  — `equity_curve` was the one field left un-cast to `float` before
  `tear_sheet()`'s math touched it
- Investigated whether partial *sells* occur in Phase 5 (previously only
  ever observed partial buys) via a constructed fixture rather than
  assumption: confirmed sells only ever hit the volume ceiling (no cash
  constraint on selling), buys can hit either
- Traced what happens to a partial sell's leftover position across
  rebalances and at forced liquidation, which led to a design question:
  `PaperSession`'s forced liquidation goes through the same fill path as any
  other order and can itself fail (partial fill or outright reject on a
  last-day price-limit lock/suspension) — unlike `Engine`'s unconditional,
  always-successful final-bar sell. Decided `liquidate_at_end` should
  default to `False` (mark-to-market, don't force-sell) rather than chase a
  guaranteed match with `Engine` that no fill-model choice can deliver
- Designed and implemented the `unliquidated_residual_cost` waterfall line:
  prices the hypothetical `TaiwanCostModel.sell_costs()` of whatever's still
  open at `sim.end`, without the sim ever submitting a sell order that could
  itself fail
- **ADR 0013** — found and fixed a real bug hiding since Phase 4:
  `reconciler.py`'s `budget_weights()`/`reconcile()` iterated over `set()`s
  of tickers, whose order is randomized per-process by Python's string-hash
  seed — a silent, non-reproducible "first come, first served" allocation
  alpha. Fixed with `sorted()` in both functions
- Traced the single-asset demonstrator's `raw_vs_adjusted` residual back to
  a deeper, Phase-1-era bug: `data/api.py::_cached_adjusted_history` bounded
  its `read_ohlcv` call to `[start, end]` but fetched a ticker's *entire*
  unbounded corporate-actions history — so a dividend recorded after the
  query's `end` (e.g. declared the following year) still back-adjusted the
  whole historical window, since every row in a bounded window is
  chronologically before a later action's ex-date. Confirmed this affects
  every caller of `get_adjusted_history`, including `Engine`, not just
  Phase 5. Fixed by adding optional `start`/`end` bounds to
  `storage.py::read_corporate_actions`, mirroring `read_ohlcv`'s existing
  pattern, wired through `_cached_adjusted_history`
- Re-ran the single-asset demonstrator after the corporate-actions fix: the
  `raw_vs_adjusted` residual barely moved (0.3404% → 0.3676%) — the fix was
  still correct and worth keeping, but not the dominant cause of the
  residual being chased (picked back up Saturday)

### Learned

- **A crash from real replay data will always find gaps a hand-built
  fixture catalogue didn't think to cover.** Both `RIGHTS_ISSUE` and
  `CAPITAL_REDUCTION` were deliberately deferred as "evidence-gated" in
  `PHASE_5.md` D15; building the demonstrator was exactly the evidence.
- **Two corporate-action types that look similar on the surface (both
  change share economics around an ex-date) can have opposite correct
  treatments** — the deciding question is whether the shareholder has a
  real choice (rights issue: yes, lapse is defensible) or the change is
  automatic and mandatory (capital reduction, in this dataset: no, a lapse
  reading would leave `LotLedger` silently stale relative to a real,
  automatic share-count change).
- **A guaranteed match between a frictionless reference and a realistic
  simulator is sometimes structurally impossible, and chasing it anyway is
  a trap.** `Engine`'s forced liquidation can't fail; `PaperSession`'s can
  (last-day halt, thin volume) — no fill-model choice closes that gap, so
  the right fix was moving the asymmetry into the reconciliation layer
  (`unliquidated_residual_cost`) instead of trying to force sim behavior to
  match.
- **Non-determinism and lookahead are the same family of bug: "same query,
  different answer."** The `set()`-ordering bug (depends on process hash
  seed) and the unbounded-corporate-actions bug (depends on wall-clock time
  relative to future data) are structurally the same failure mode —
  reproducibility, not just narrow lookahead-safety, is the thing to keep
  auditing for.
- **A real, justified fix doesn't have to close the specific gap that
  motivated finding it.** The corporate-actions bound fix was correct and
  worth keeping regardless of its small effect on this particular
  residual — self-consistency matters even when it doesn't move the number
  you were chasing.

- Ran the live smoke test for real for the first time (previous runs had
  always hit a stale local store): 14 bars processed against genuinely
  fresh data, no crash — session 1 of the ~14 needed for `PHASE_5.md`'s
  live-connectivity exit criterion

### Learned

- **A continuous, modest difference can become a large one if the code path
  it feeds into makes a discrete decision.** The cross-sectional ticker-set
  divergence isn't a bigger version of the single-asset price-basis gap —
  it's the same gap filtered through `reconcile()`'s exact `delta == 0`
  integer check, which has no tolerance band, so a difference that would
  otherwise show up as a slightly different trade size instead shows up as
  a trade happening in one engine and not the other, compounding forward
  through every subsequent month's starting portfolio state.
- **Splitting an already-entangled multi-fix diff into atomic commits after
  the fact is real, nontrivial work**, not just `git add -p` — when three
  unrelated fixes land in the same functions across a session, cleanly
  separating them requires reconstructing each intermediate file state by
  hand and re-testing at each stage, not just picking hunks.
- **Testing a "live" data path by batch-replaying an already-accumulated
  window is not the same test as running it live, day by day** — the
  freshness check and the daily session-boundary logic only actually fire
  under the second pattern. Recognizing this distinction is what turned
  "wait two weeks and run once" from a shortcut into a design mistake.
